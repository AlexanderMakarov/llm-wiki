# Maintainer guide

This directory is the governance scaffold for llmwiki maintainers.
Contributors should read [`../../CONTRIBUTING.md`](../../CONTRIBUTING.md)
first — it has the short version of what this folder covers in detail.

| File | What it's for |

| [`ARCHITECTURE.md`](ARCHITECTURE.md) | One-page system diagram + layer boundaries + what NOT to add |

## Slash commands

Five commands drive maintainer work, all from this repo's `.claude/commands/` — Claude Code picks them up when it opens the repo, and `llmwiki install-agent-kit` never ships them (the vault commands it does ship are in [`../reference/slash-commands.md`](../reference/slash-commands.md)).

Hand-written llmwiki governance:

- `/maintainer` — meta-skill that loads every doc in this folder and surfaces the triage / release next actions; start here before anything governance-related.
- `/release <version>` — thin wrapper that loads [`.claude/skills/release/SKILL.md`](../../.claude/skills/release/SKILL.md) and follows [`RELEASE_PROCESS.md`](RELEASE_PROCESS.md): preflight on `main` → version bump → CHANGELOG/UPGRADING editorial → local commit+tag → human gate before push → watch `release.yml`.
- `/triage-issue <issue-number>` — applies the `TRIAGE.md` label taxonomy, milestone and priority to a new issue.

Generated by AWOS from the delivery decisions in [`../../context/product/delivery-flow.md`](../../context/product/delivery-flow.md) — to change how they behave, change those decisions and re-run the flow command instead of hand-editing the command files:

- `/fix-bug <issue>` — one bug through diagnosis → scoped fix + regression test → verify → independent review → PR, amending the owning spec when behaviour changed.
- `/implement-feature <spec-or-issue>` — one feature through the AWOS chain (spec → tech → tasks → implement → verify) → independent review → PR.

`/release` is the only one that also has a Cursor wrapper; the other four are Claude-only, which [#227](https://github.com/AlexanderMakarov/llm-wiki/issues/227) tracks.

Code review uses `REVIEW_CHECKLIST.md` directly (or via the single independent review stage inside `/implement-feature` / `/fix-bug`, where the coding agent picks its own most suitable review skill or command).

The nine `/awos:*` commands are a separate layer — `.claude/commands/awos/` plus the flat `.cursor/commands/awos-*.md` wrappers, both generated from `.awos/commands/` by `scripts/sync-awos-cursor-commands.sh`. Of those, `product`, `roadmap`, `architecture` and `hire` are the human-invoked ones that populate `context/product/`; `spec`, `tech`, `tasks`, `implement` and `verify` are invoked internally by `/implement-feature` and are not normal entry points.

See `.claude/commands/` (and `.cursor/commands/` for Cursor-facing wrappers) in the repo root for the source of each command.

## When things go wrong

- **CI red on `main`** → fix-first, roll forward, never force-push
- **Security issue reported** → see `SECURITY.md` in the repo root
- **Contributor PR stuck > 7 days** → escalate via the triage pass
  (there's a rule in `TRIAGE.md`)
- **Someone re-proposes a declined idea** → link them to the
  entry in `DECLINED.md`

## Why a dedicated maintainer folder?

Because maintainer docs have a different audience than user docs.
User docs go in `docs/` (rendered on the site). Maintainer docs
stay here — they're less polished, more operational, and they
change with the team rather than with releases.

Keep this folder short. When a doc is over one screen, prune.
