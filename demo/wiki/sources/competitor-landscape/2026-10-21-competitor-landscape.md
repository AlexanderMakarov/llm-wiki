## Summary

This source is a competitive positioning document comparing llmwiki with three other tools that persist memory for coding agents: agentmemory, mem0, and TencentDB Agent Memory. It contrasts them across a grid of functions (output mechanism, context impact, agent coverage, query features, resource usage, token cost, observability). It also clarifies that two similarly named projects (lucasastorian's llmwiki and the Karpathy LLM Wiki Obsidian plugin) solve a different problem, and lists situations where llmwiki is not the right choice.

## Key Claims

- llmwiki delivers memory to agents through MCP tool calls, so nothing is injected into the prompt, and it adds only six MCP tool descriptions to context.
- llmwiki supports eleven agents (Claude Code, Codex CLI, ChatGPT, Copilot Chat, Copilot CLI, Cursor IDE, Cursor CLI, Gemini CLI, Obsidian, OpenCode, OpenClaw), versus 25 for agentmemory, any for mem0, and 9 for TencentDB Agent Memory.
- llmwiki uses no LLM for search, sync, or reading raw pages; an LLM is used only for `synth`.
- llmwiki's runtime has no database, numpy, torch, or node; its only runtime dependency is Python 3.12+ with `markdown`.
- llmwiki's `build` writes a static site that exposes pipeline state, token and cache metrics, health, and the candidate queue for a human observer.
- agentmemory's default MCP context cost is 54 tool descriptions when its server is up, plus a recall of up to about 2000 tokens by default.

## Key Quotes

> "The static site is how a person observes llmwiki's vault. It is not the memory." — the document separates the human-facing view from the agent-facing memory store.

> "Nothing stays running. MCP starts with the agent session and exits with it." — the basis for llmwiki's resource-usage positioning against always-on servers.
