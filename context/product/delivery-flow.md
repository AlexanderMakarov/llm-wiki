## 1. Feature Description Source

- **Source:** GitHub Issue (number, URL, or title search); plain prompt text; local file path; and/or a pre-written spec already under `context/spec/` (resume mid-chain). Bug reports for `/fix-bug`: GitHub Issues only.
- **Fetch transport:** Primary `gh` CLI (`gh issue view`, `gh issue list`, `gh api`). Fallback: GitHub MCP tools in the session if `gh` is unavailable. No `context/sources/sources.md` configured.
- **Normalization:** Issue number/ID, title, body, labels, acceptance hints from checklists in the body, HTML URL. For prompt/local-file: title + requirements text. For pre-written specs: `SPEC_NAME` directory under `context/spec/`.
- **Pre-generated specs:** Yes — inspect `context/spec/{SPEC_NAME}/` and resume from the first missing artifact (`functional-spec.md` → `technical-considerations.md` → `tasks.md` → implement). With no input, resume from the next incomplete `context/product/roadmap.md` item.
- **Surrounding context to pre-seed `/awos:spec`:** Issue body and comments, plus linked issues, attachments, and URLs referenced in the issue (fetched via `gh`). Record unreachable links rather than silently skipping. Prompt/local-file sources: none.
- **Done / skip-work signals:** GitHub Issue `state=closed`; owning AWOS spec Status `Completed` (or all `tasks.md` items `[x]`); or a merged PR for the same work already exists.

## 2. Git Flow

- **Base branch:** `origin/main` (workflows also list `master` for upstream legacy — feature work targets `main`)
- **Branch naming:** `feat/<issue>-<short-slug>` for features; `fix/<issue>-<short-slug>` for bug fixes; example `feat/97-candidates-review`
- **Submodules:** none (probed: no `.gitmodules`)
- **Target sync & conflicts:** Rebase onto `origin/main` — checked before opening the PR and again before merging. Conflicts resolved by a subagent; non-trivial resolutions confirmed with the user; local gates (`ruff` + `pytest`) re-run after any sync
- **Worktrees:** viable — preferred isolation for `/implement-feature` and `/fix-bug`. No project `worktree-init` skill; use the exact recipe below.
  - **Create / bring-up (verbatim):**
    ```bash
    git fetch origin main
    BRANCH="feat/<issue>-<short-slug>"   # or fix/<issue>-<short-slug>
    WT_SLUG=$(echo "$BRANCH" | tr '/' '-')
    WT=".claude/worktrees/$WT_SLUG"       # already gitignored
    git worktree add -b "$BRANCH" "$WT" origin/main
    cd "$WT"
    LLMWIKI_SKIP_AUTOMATION=1 ./setup.sh
    # Isolated throwaway vault — NEVER copy primary checkout config.json (may point at live Obsidian)
    TMP_VAULT="$WT/.worktree-vault"
    mkdir -p "$TMP_VAULT"
    printf '%s\n' "{\"vault\":{\"default_path\":\"$TMP_VAULT\"}}" > config.json
    python3 -m llmwiki init --vault "$TMP_VAULT"
    python3 -m pytest tests/ -q
    ```
  - **Always drive the worktree package:** `python3 -m llmwiki …` from `$WT` (or `pip install -e .` into a worktree venv). Do **not** rely on PATH `llmwiki` — that entrypoint loads the primary package + primary `config.json` and can hit the live vault.
  - **Write / mutate isolation:** every agent-driven `sync`, `build`, `synth` (non-estimate), ingest, or other vault-mutating command targets `$TMP_VAULT` (via worktree `config.json` or explicit `--vault` / `--out` / `--dir`). Parallel worktrees must not share that tmp vault path.
  - **Read-only live vault:** the agent **may** run clearly non-mutating probes against the live vault path from the primary checkout's `vault.default_path` (examples: `lint`, `synth --estimate`, status/read helpers). Never write `raw/`, `wiki/`, or `site/` under the live vault from the agent.
  - **Operator live verification:** at the user smoke-confirm step, do **not** run mutating `llmwiki` against the live vault. Instead print ready-to-paste commands that use the **worktree code** against the live vault path (e.g. `cd $WT && python3 -m llmwiki build --vault <LIVE> --out <LIVE>/site`, then open `<LIVE>/site/index.html`). The operator runs those commands themselves.
  - **Cleanup (when discarding the worktree):** `git worktree remove "$WT"` (after commit/push or stash); delete throwaway vault with the directory.
- **Sanctioned verification path:** Automated criteria — `pytest` + `python3 -m llmwiki` against `$TMP_VAULT`; UI — `python3 -m llmwiki build` then Playwright on `$TMP_VAULT/site`, opened as files. Live Obsidian vault mutation is never automated — only operator-pasted commands at smoke confirm. Prefer driving the built files yourself over asking the user to run routine verify.

## 4. Review

1. **User smoke confirm** — after `/awos:verify`, pause until the user confirms the feature (or fix) works as expected; include the live-vault command block from §2; do not start local review beforehand
2. **Local single review (pre-push, on branch)** — one independent review pass on `git diff origin/main...HEAD`. The coding agent picks its own most suitable review skill, command, or subagent for that pass (do not hardcode a product-specific reviewer name). Fixed prompt (not author-framed focus): load and apply `docs/maintainers/REVIEW_CHECKLIST.md` plus companion docs `docs/maintainers/ARCHITECTURE.md`, `docs/maintainers/DECLINED.md`, `CONTRIBUTING.md`, and `SECURITY.md`. Encode checklist priority via its own Blocker vs Nit rule — Security + Meta + layer-boundary / failing tests-build first as blockers; Code quality / Docs / smoke as nits unless they trip Meta or Security. Write the full review to `context/spec/{SPEC_NAME}/review.md`. The reviewer returns only verdict, counts by severity, and path. The orchestrator then Reads the review file and **prints the full body in chat**, pauses for keep/drop, and applies accepted findings before push. There is no second reviewer. **Session-only artifact (#159):** still write `review.md` / `review-*.md` locally for keep/drop and chat; **never stage or commit** those files. `context/.gitignore` ignores `**/review.md` and `**/review-*.md` so `git add context/…` cannot pick them up.
3. **Local static gate** — `ruff check llmwiki tests scripts` and `python3 -m pytest tests/ -q` before push
4. **CI on the pull request** — wait for required GitHub Actions and fix failures in a loop (diagnose failed job logs via `gha-diagnosis` skill + `gh run view --log-failed` → fix → push → re-check). Typical CI job ~1–2 minutes; path-filtered E2E/browser jobs up to ~8–15 minutes
5. **Not in the automated wait set** — Claude-in-CI workflows were removed (#116); do not wait on a Claude Code Review check. CODEOWNERS human approval is not polled by the flow (maintainer may still review out-of-band)

- **Approval gates:** Two pauses — stop after `/awos:spec` and again after `/awos:tech` for document review. `tasks.md` has **no document gate**. Upstream `/awos:tasks` Step 4 ("Present Draft and Refine") normally interviews until the user is satisfied — under `/implement-feature` only, that draft-review loop is suppressed: write `tasks.md`, report a short slice summary in chat (not an Approve ask), and continue to implement. The user may still revise in chat or by re-running `/awos:tasks`. Standalone `/awos:tasks` (outside this flow) keeps its full draft loop.
- **Change-request timing:** Open the PR only after local single review + static gate succeed
- **Max-wait & escalation:** Watch PR checks up to ~30 minutes (`gh pr checks --watch` / Monitor equivalent); on timeout ask whether to keep watching or hand off. Poll interval ≥30s. Never wait forever. Escalate in chat (and via §9 only if it qualifies as an exception event)

## 5. Delivery

- **Mode:** Merge-when-ready to `main`; packaging/releases stay batched via `/release` + version tags (not part of this flow)
- **Merge policy:** The flow merges via `gh pr merge` once gates are green — always behind a fresh per-run user confirmation; skipped/unanswered confirmation means do not merge
- **Post-merge CI:** Watch base-branch pipelines after merge; diagnose and fix forward on `main` if they fail
- **Approvals:** Spec/tech document gates; user smoke confirm; local review keep/drop; per-run merge confirm
- **Versioning:** Unchanged by this flow — version bumps live in `/release` / `pyproject.toml` when cutting a release
- **Deployment:** Never auto-deploy from this flow — releases stay on `/release` + tags when chosen manually
- **Ticket state transitions:** n/a — do not transition or close GitHub Issues from this flow (even when the task came from an issue)
- **Definition of Done:** PR merged (after per-run confirm) and post-merge required checks green; report evidence to the user (PR URL, merge commit, local review verdict/counts/path). Issues left untouched

## 8. Context Strategy

How the generated command keeps its context window small — one long window degrades judgment (worst exactly at review time) and inflates cost.

- **Mode:** single session with subagent-isolated stages
- **Stages isolated in subagents:** `fetch-ticket` / `fetch-bug` (mechanical `gh`); resume preflight (cheap); conflict resolution during rebase; CI log triage + fix coding; independent local-review pass; bug `diagnose` / `fix` / `regression-test` coding tasks; non-interactive portions of verify when no user interview is needed
- **Stages kept in the main context:** `/awos:spec`, `/awos:tech`, `/awos:tasks` (spec/tech still interview; tasks under `/implement-feature` skips the draft Approve ask per §4); `/awos:implement` (dispatches subagents — cannot nest); `/awos:verify` when it must `AskUserQuestion` for undrivable criteria; approval gates (spec/tech); user smoke confirm (including live-vault command handoff); local-review presentation (Read `review.md` → print full body in chat) and keep/drop; merge confirmation; exception PR comments that need the open PR number
- **Flow log:** Always `context/spec/{SPEC_NAME}/flow-log.md` — features, attached bug fixes, and orphan fix-as-spec directories (`{issue}-{short-slug}`) share the same filename (#164). Committed with the work and finalized at commit-push; stop writing once the PR is opened or merged.
- **Review files:** written next to the log as `context/spec/{SPEC_NAME}/review.md` but **gitignored / never committed** (#159)
- **Model tiers:** Fast tier — ticket/bug fetch, resume checks, CI polling, first-pass log triage. Strongest tier — spec/tech interviews, classification, diagnosis, local reviews, validating CI fixes

## 9. Notifications

Where the flow announces itself so the team stays aware as gates are removed — "human on the loop", not "in the loop".

- **Channel:** GitHub pull request comments via `gh pr comment` — **exceptions only**. Routine progress (PR opened, CI/gates progress, gates passed, merged, deployed, blocked-and-waiting) is reported to the **user in chat**, never as a PR comment. Background: PR #119 comments for open / gates-passed / merged duplicated information already visible on the PR and were judged noise.
- **Announce on (PR comment required):**
  1. **Implementation divergence** — chosen approach differs materially from the approved `functional-spec.md` / `technical-considerations.md` (document what changed and why)
  2. **Major post-implementation issue** — verify failure that forces a scope/approach change, or a serious local-review finding that alters the delivered behavior
  3. **Parallel / overlapping work** — rebase or review surfaces functional overlap with another change (competing PR, colliding feature area); describe the overlap and the resolution chosen
- **Do not announce on:** change request opened; CI red / max-wait; gates passed; merged; deployed; “ready to try” try-steps (those stay in the chat close-out report)

## Bug-fix Flow

Whether `/awos:flow` generated the lighter bug-fix command (named in **Generated Commands** above), and its policy. Flow-agnostic — the bug-fix command consumes §1–§9 above and only its middle stages differ.

- **Generated:** yes — `/fix-bug` → `.claude/commands/fix-bug.md`
- **Bug source:** GitHub Issue
- **Classification & amendment policy:** Always classify conformance (fix code + regression test, leave spec) vs divergence (fix + regression test + amend owning `functional-spec.md` via `/awos:spec` update mode). When there is no pre-existing owning spec, allocate a regular `context/spec/{issue}-{short-slug}/` directory for the run’s log and review (and any minimal notes the fix needs); full functional-spec authoring stays optional for pure conformance fixes with nothing to document.
- **Regression-test expectation:** One failing→passing test capturing the bug, honoring `<!-- skip-tests: true -->` on the owning spec's `tasks.md` when one exists
- **Per-bug artifacts (#164):** Always under `context/spec/{SPEC_NAME}/` with `flow-log.md` + session-only `review.md`. Orphan fix → create `context/spec/{issue}-{short-slug}/` (same layout as a feature spec).
