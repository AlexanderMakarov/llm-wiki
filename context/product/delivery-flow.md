## 4. Review

1. **User smoke confirm** — after `/awos:verify`, pause until the user confirms the feature (or fix) works as expected; do not start local review beforehand
2. **Local dual review (pre-push, on branch)** — (a) apply `docs/maintainers/REVIEW_CHECKLIST.md` and the same governance docs `/review-pr` loads, against `git diff origin/main...HEAD` (and write findings to `context/spec/{SPEC_NAME}/review.md`); (b) dispatch Cursor `code-reviewer` (`Agent`/`Task` `subagent_type="code-reviewer"`) on the same branch diff independently. Present both reviews; keep/drop decisions; apply accepted findings before push. Do **not** invoke `/review-pr <n>` here — that command stays for reviewing someone else's open PR by number
3. **Local static gate** — `ruff check llmwiki tests scripts` and `python3 -m pytest tests/ -q` before push
4. **CI on the pull request** — wait for required GitHub Actions and fix failures in a loop (diagnose failed job logs via `gha-diagnosis` skill + `gh run view --log-failed` → fix → push → re-check). Typical CI job ~1–2 minutes; path-filtered E2E/browser jobs up to ~8–15 minutes
5. **Not in the automated wait set** — Claude Code Review Action is soft-fail/advisory (do not block the flow on it); CODEOWNERS human approval is not polled by the flow (maintainer may still review out-of-band)

- **Approval gates:** Two pauses — stop after `/awos:spec` and again after `/awos:tech` for document review. `tasks.md` has no gate — `/awos:implement` starts right after `/awos:tasks`
- **Change-request timing:** Open the PR only after local dual review + static gate succeed
- **Max-wait & escalation:** Watch PR checks up to ~30 minutes (`gh pr checks --watch` / Monitor equivalent); on timeout ask whether to keep watching or hand off. Poll interval ≥30s. Never wait forever

## 5. Delivery

- **Mode:** Merge-when-ready to `main`; packaging/releases stay batched via `/release` + version tags (not part of this flow)
- **Merge policy:** The flow merges via `gh pr merge` once gates are green — always behind a fresh per-run user confirmation; skipped/unanswered confirmation means do not merge
- **Post-merge CI:** Watch base-branch pipelines after merge; diagnose and fix forward on `main` if they fail
- **Approvals:** Spec/tech document gates; user smoke confirm; local review keep/drop; per-run merge confirm
- **Versioning:** Unchanged by this flow — version bumps live in `/release` / `pyproject.toml` when cutting a release
- **Deployment:** Never auto-deploy from this flow — releases stay on `/release` + tags when chosen manually
- **Ticket state transitions:** n/a — do not transition or close GitHub Issues from this flow (even when the task came from an issue)
- **Definition of Done:** PR merged (after per-run confirm) and post-merge required checks green; report evidence to the user (PR URL, merge commit, local review verdict/counts/path). Issues left untouched

## 8. Context Strategy

How the generated command keeps its context window small — one long window degrades judgment (worst exactly at review time) and inflates cost.

- **Mode:** single session with subagent-isolated stages
- **Stages isolated in subagents:** `fetch-ticket` / `fetch-bug` (mechanical `gh`); resume preflight (cheap); conflict resolution during rebase; CI log triage + fix coding; `code-reviewer` review pass; bug `diagnose` / `fix` / `regression-test` coding tasks; non-interactive portions of verify when no user interview is needed
- **Stages kept in the main context:** `/awos:spec`, `/awos:tech`, `/awos:tasks` (each uses `AskUserQuestion`); `/awos:implement` (dispatches subagents — cannot nest); `/awos:verify` when it must `AskUserQuestion` for undrivable criteria; approval gates (spec/tech); user smoke confirm; local dual-review presentation and keep/drop; merge confirmation; notification posts that need the open PR number
- **Flow log:** `context/spec/{SPEC_NAME}/flow-log.md` (or `context/fix-log-{BUG_ID}.md` for bug fixes with no owning spec) — committed with the work and finalized at commit-push; stop writing once the PR is opened or merged
- **Model tiers:** Fast tier — ticket/bug fetch, resume checks, CI polling, first-pass log triage. Strongest tier — spec/tech interviews, classification, diagnosis, local reviews, validating CI fixes
